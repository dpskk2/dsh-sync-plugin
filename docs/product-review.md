# 曝光与上手体验审查

审查日期：2026-09-17。对象：本地 `dsh-sync-plugin`，包版本 0.12.3。本轮侧重发现、理解、安装与首次双机使用，不是同步引擎的全面正确性审计。

## 核心判断

项目已经有明确需求：个人在多台电脑间继续 DSH 工作。原有介绍却首先销售“云文档、CRDT、跨机收敛”，用户读完仍不知道第二台怎么接入、同步成功长什么样、为什么模型配置到了但不能使用。

建议统一用 **DSH Sync · 换台电脑，接着做** 作为展示名，继续保留 `dsh-sync-plugin` 包名。把“会话 + 工作区文件”放在场景前台，把合并算法放到技术文档。不要为了营销重新起一个不可搜索、需要迁移安装的包名。

## 发现与本轮处理

| 问题 | 对用户的影响 | 本轮处理 |
| --- | --- | --- |
| “给 DSH 带来变成云文档的体验”抽象且不顺口 | 很难在卡片和分享时解释用途 | 改成具体换机场景、简短中英简介 |
| CRDT、Lamport 等实现细节过早出现 | 非技术用户在安装前被迫理解算法 | 首页改为场景 → 安装 → 第二台 → 范围 → 排障 |
| 自动建仓藏在提示中，主流程先要求手写 JSON | 增加首次尝试成本 | 推荐流程改为登录 gh 后点同步，保留手动方案 |
| 没有完整第二台接入和验收流程 | 上传一次就误以为完成了同步设置 | 增加双向测试会话验收 |
| “2 分钟”“永不丢失”“API 密钥不上云”过强 | 真实边界一出现就损害信任 | 删除时长保证，说明专用凭据排除与合并取舍 |
| 设置页只有自动重启等高级开关 | 核心偏好需要编辑文件，高级修复反而更显眼 | 增加手动 / 自动模式与工作区文件开关，含失败重试、保存结果 |
| 设置页仍称新冲突会要求人工裁决 | 与新版引擎说明相冲突 | 更名为历史冲突副本，按实际策略解释 |
| 配置文件变更被说成即时生效 | 自动模式开关保存后不运行，像“坏了” | 明确重启要求，状态称“已配置”而非声称调度正在运行 |
| 同步范围文档停留在旧版本 | 用户照旧口径判断设置合并、垃圾文件排除 | 按当前源码重写，历史设计标明历史性质 |
| README 测试命令指向仓库外脚本 | 普通 clone 无法复现 | 增加仓库内测试入口与 CI，明确尚未覆盖完整引擎 |
| npm 包不含教程、英文入口薄弱 | 安装后缺少可查文档 | 包含用户文档，增加英文教程与错误反馈模板 |

## 下一轮优先级

### P0：推广前补足的可信度

1. **已有公开仓库不能只打日志后继续自动复用。** `lib/sync.js` 的 `bootstrapRemote()` 检查到 PUBLIC 仍返回地址。建议自动引导拒绝复用公开仓库，并显示可操作的错误；手动地址路径也需要明确可见性校验策略。本轮纠正文案，未改同步引擎。
2. **备份分支名称不代表上传成功。** `backupRemoteHead()` 在推送失败时仍返回本地备份分支名。本轮已将 UI 的“远端备份分支”改为“备份分支（可能仅在本机，请检查备份推送日志）”；后续仍应由引擎明确返回本地已保存、远端已保存和备份失败三种状态。
3. **把核心引擎测试收进仓库并阻止未测版本发布。** 现在新增的是设置交互和既有补丁验证；主数据合并、工作区合并、公开仓库场景、第二台首次接入仍需要可移植回归及发布门禁。

### P1：真正降低上手成本

1. 在首次使用页显示四项检查：Git 可用、GitHub 已登录、仓库是私有、首次传输结果。现在只有说明文字和 Git 状态，尚无完整可视化向导。
2. 提供经过校验的“连接已有仓库”表单，展示账号与仓库可见性。当前后端刻意不允许浏览器修改 `remote`，本轮未绕过这层白名单。
3. 显示待上传目录、文件数量、体积和排除项预览，让“同步工作区文件”成为看得见范围的选择。
4. 模式切换后重新注册定时器，减少一次重启；同时区分配置模式与实际运行状态。当前先明确提示重启。
5. 用测试环境录制 20–30 秒真实演示：A 新建会话 → 点同步 → B 同步 → 看见同一会话与文件。字幕只写用户动作，脱敏账号、路径和会话。当前 SVG 明确是流程图，不能当作功能演示截图。

### P2：分发与传播

1. 保持 GitHub About、npm 简介、目录双语条目同一口径。GitHub 已有 `dsh-plugin`、`dsh`、`deepseek-harness`、`sync`、`backup` topics，不把补标签当成新的增长成果。
2. 核对目录是否已收录；已有则更新，不重复投稿。配合真实截图，并按当时目录的截图字段规范提交。
3. 发布新版时写“现在能少做哪一步”，避免用内部修复编号作为唯一标题。文案见 [发布素材](launch-copy.md)。
4. 英文 README 已具备基本安装与换机路径；下一步再考虑界面国际化，当前 UI 仍主要为中文。

## 如何判断优化有效

不预设增长百分比。发布前后各记录一段相同长度的时间窗口，对比 GitHub 仓库访问 / clone、npm 下载、目录带来的反馈；这些是粗指标，不能当作独立活跃用户。

更值得先做一次小规模新手测试：请未参与开发的人按 README 接通两台测试电脑，记录完成比例、耗时、卡点、是否误解本地快照、是否能找回 API 配置。目标是减少失败步骤和重复答疑，不往用户会话中额外埋遥测。
